# Project instructions

## Мок-данные — обязательное правило

Всегда добавляй моковые (тестовые) данные везде, где приложение/код ожидает данные, но реального источника ещё нет. Это правило действует по умолчанию и не требует отдельного запроса.

### Когда добавлять мок-данные
- Новые компоненты, страницы, экраны, которые что-то отображают.
- Списки, таблицы, карточки, графики, профили, чаты, сообщения, уведомления.
- API-запросы, хуки загрузки данных, сервисы, сторы, репозитории.
- Формы с предзаполненными полями, выпадающие списки, фильтры, значения по умолчанию.
- Состояния загрузки/пустоты/ошибки — наполняй их реалистичными примерами.

### Как оформлять мок-данные
- Держи мок-данные в отдельном, явно названном месте (например, `mock/`, `mocks/`, `fixtures/`, `__mocks__/` или файл `*.mock.ts`), а не разбрасывай их по логике.
- Давай понятные имена: `mockUsers`, `mockChatMessages`, `mockProducts`.
- Делай данные реалистичными и разнообразными: реальные по смыслу имена, тексты, даты, числа, статусы, идентификаторы. Не используй `foo`, `bar`, `test1` без необходимости.
- Покрывай крайние случаи там, где это уместно: длинный текст, пустой список, много элементов, разные статусы/роли, даты в прошлом и будущем.
- Мок-данные должны соответствовать реальной модели/типам/схеме данных. Если есть типы — типизируй мок-данные этими типами.
- Добавляй комментарий `// TODO: заменить на реальные данные` рядом с точкой интеграции моков.
- Не смешивай мок-данные с продакшн-логикой: подключай их через явный слой/флаг (например, `USE_MOCKS`, переменная окружения), чтобы их было легко убрать.

### Как подключать
- Если реальный бэкенд/API уже есть — используй его; мок-данные добавляй только как запасной вариант/fallback или для отсутствующих сущностей.
- Если бэкенда нет — сначала делай мок-данные, чтобы интерфейс и логика были рабочими и проверяемыми end-to-end.
- Сохраняй совместимость с реальным контрактом: форма ответа моков должна совпадать с ожидаемой формой реального API.

### Не делать
- Не оставлять компоненты/экраны без данных, если по правилу требуются мок-данные.
- Не использовать мок-данные как причину не реализовать логику, которую можно реализовать сейчас.
- Не хардкодить мок-данные глубоко внутри компонентов, если их можно вынести в общий слой.
